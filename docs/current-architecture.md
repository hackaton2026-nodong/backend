# Current Architecture Review

이 문서는 현재 구현이 `Company + User + Case + Document` 기준서 방향을 얼마나 만족하는지, 그리고 구조적으로 어떤 부채가 남아 있는지를 정리한 검토 문서다.

## 1. 기준서 대비 만족한 부분

현재 구현은 아래 항목을 이미 만족한다.

- 회사 관리자 가입 시 회사 생성과 사용자 소속 연결이 함께 일어난다.
- 초대코드 기반 회사 가입 흐름이 존재한다.
- `User -> Company(Enterprise) -> Case -> Document` 연결 축이 서비스 레벨에서 형성되어 있다.
- 문서 업로드가 메타데이터 생성이 아니라 실제 파일 업로드로 전환되었다.
- 문서 저장 후 SHA-256 해시 생성이 추가되었다.
- 문서 상태 머신의 초기 단계인 `UPLOADED`, `STORED`, `HASHED`가 실제로 사용된다.
- 문서 해시 기반 EIP-712 서명 요청/제출 API가 연결되었다.
- Stub relayer 기반 앵커링 API가 연결되어 `anchorId`, `txHash`, `blockNumber` 저장 흐름을 수동 검증할 수 있다.
- 오프체인 분석 결과 저장 모델과 placeholder API가 연결되었다.
- 같은 회사 사용자만 케이스에 접근하도록 검사한다.
- 문서 원문 접근을 케이스 당사자 또는 관리자 수준으로 제한한다.
- 저장, 해시, 앵커링을 포트/어댑터 구조로 분리할 기반을 만들었다.

현재 기준으로 보면, "문서 업로드 기능을 현재 프로젝트 구조에 최소 수정으로 녹였다"는 목표는 달성됐고, 문서 해시 기반 서명/Stub 앵커링 MVP까지 수직 검증 가능한 상태다.

## 2. 아직 기준서와 정확히 일치하지 않는 부분

아래 항목은 방향은 맞지만 아직 완성 상태는 아니다.

### 2.1 Company 명칭

- 코드 내부에서 회사 엔티티 이름은 아직 `Enterprise`다.
- API는 `/api/companies`를 추가했지만 `/enterprises`도 동시에 남아 있다.

의미:

- 기준서의 `Company` 모델을 실질적으로 구현하고는 있지만, 용어 레벨의 정리는 끝나지 않았다.

### 2.2 Document 모델의 연관관계

- `Document`는 `caseId`, `uploaderUserId`를 원시 필드로 들고 있고 JPA 연관관계는 없다.

의미:

- 최소 수정 관점에서는 허용 가능하지만, 장기적으로는 `Case`, `User`와의 객체 관계가 없어서 조회 확장성과 무결성 표현이 약하다.

### 2.3 권한 모델

- `Role`과 `UserType`이 동시에 존재한다.
- 일부 로직은 `Role`, 일부 로직은 `UserType`을 기준으로 동작한다.

의미:

- 현재는 가입 시 값을 맞춰 주고 있어서 동작은 가능하지만, 권한 판단 기준이 둘로 나뉘어 구조적으로 깔끔하지 않다.

### 2.4 파이프라인 후속 단계

- 앵커링 API는 연결됐지만 실제 Sepolia RPC 전송은 아직 Stub relayer다.
- EIP-712 typed data hash, `caseIdHash`, `anchorId` 계산은 현재 MVP 내부 검증용 SHA-256 helper 기반이다.
- 실제 ECDSA signer recovery 검증은 아직 없다.
- 분석 저장 모델은 생겼지만 OCR, 구조화, AI 분석 RPC는 아직 placeholder다.
- 문서 업로드 후 분석과 온체인 증명은 같은 `documentId`/`sha256Hash`를 공유하는 별도 분기 플로우로 다뤄야 한다.

의미:

- 기준서의 `Document 중심 처리 축` 중 업로드/해시/서명/Stub 앵커링 저장 축은 MVP로 연결됐고, 실제 체인 전송과 실제 오프체인 분석은 후속 구현이다.

## 3. 구조적으로 옳은 부분

현재 구조에서 특히 맞게 잡힌 부분은 다음과 같다.

### 3.1 최소 수정 원칙

- 기존 `enterprise`, `user`, `cases`, `document` 패키지를 유지하면서 축만 재배치했다.
- 전체 리네이밍보다 기능 우선 전환을 택했기 때문에 구현 리스크가 낮다.

### 3.2 문서 처리 포트 분리

- `FileStoragePort`
- `DocumentHashPort`
- `DocumentAnchorPort`
- `DocumentAnchorRelayerPort`

이 분리는 이후 S3, 실제 블록체인, 외부 OCR로 확장할 때 적절한 방향이다.

### 3.3 권한을 서비스에 붙인 방식

- 케이스 접근은 회사 기준으로 먼저 제한한다.
- 문서 접근은 케이스 당사자 또는 관리자 수준으로 더 좁힌다.

이 순서는 기준서의 접근 제어 모델과 잘 맞는다.

## 4. 구조적으로 남아 있는 문제

아래는 현재 문서에 반드시 명시해야 하는 실제 구조적 문제다.

### 4.1 `POST /api/companies`의 의미가 애매하다

- 관리자 가입 시에도 회사가 생성된다.
- 별도로 `POST /api/companies`도 존재한다.
- 이 엔드포인트는 현재 인증 사용자의 역할 검증 없이 호출 가능하다.

영향:

- "회사는 관리자 가입으로만 생성한다"는 규칙이 약해진다.
- 로그인한 일반 사용자도 회사를 새로 만들 수 있는 구조다.

권장 후속 조치:

- `POST /api/companies`를 관리자 전용으로 제한하거나 제거한다.
- 회사 생성 책임을 signup 흐름과 명확히 구분한다.

### 4.2 `Role`과 `UserType` 중복

- `ADMIN`, `EMPLOYER`, `WORKER`가 이미 역할에 존재한다.
- 동시에 `UserType.EMPLOYER`, `UserType.WORKER`도 별도로 유지된다.
- `DashboardService`, `CaseService`는 여전히 `UserType` 의존이 강하다.

영향:

- 새 기능이 추가될수록 두 필드가 어긋날 위험이 커진다.

권장 후속 조치:

- 권한 판단 기준을 `Role`로 단일화하고 `UserType`은 제거하거나 표시용으로 축소한다.

### 4.3 JPA 스키마 마이그레이션 부재

- 운영 설정은 `ddl-auto: none`이다.
- 하지만 회사/초대코드/문서 저장 구조 변경에 필요한 DB 마이그레이션 파일은 없다.

영향:

- 운영 DB에는 현재 엔티티 구조가 자동 반영되지 않는다.

권장 후속 조치:

- Flyway 또는 Liquibase를 도입하고 현재 변경분을 migration으로 명시한다.

### 4.4 `Document` 대표 상태와 하위 상태의 역할 분리

- `DocumentStatus`에 서명/앵커/분석과 관련된 대표 상태가 포함되어 있다.
- 동시에 `DocumentSignatureStatus`, `DocumentAnchorStatus`, `DocumentAnalysisStatus`가 별도 하위 상태로 존재한다.
- 장기적으로는 문서 자체 상태는 업로드/저장/해시 중심으로 단순화하고, 서명/앵커/분석 진행률은 하위 테이블 상태를 기준으로 보는 편이 안전하다.

영향:

- 현재 MVP에서는 대표 상태로 화면 흐름을 단순하게 보여줄 수 있다.
- 기능이 늘어나면 대표 상태 하나에 모든 비동기 작업 상태를 섞는 구조가 복잡해질 수 있다.

권장 후속 조치:

- 사용자 화면에서는 `Document`, `DocumentSignature`, `DocumentAnchor`, `DocumentAnalysisResult` 상태를 조합해 표시한다.
- 백엔드 내부 오케스트레이션은 분석 플로우와 온체인 증명 플로우를 분리한다.

### 4.5 실제 오케스트레이션 부재

- 현재 테스트 페이지는 업로드, 서명 요청, 지갑 연결, 서명 제출, 앵커링, 분석 placeholder를 한 화면에서 수동 버튼으로 호출한다.
- 실제 사용자 플로우에서는 문서 업로드 후 분석은 자동 시작하고, 지갑 서명 이후 서명 제출과 앵커링은 자동으로 이어지는 구성이 자연스럽다.

영향:

- MVP 검증은 가능하지만, 제품 UX로는 아직 개발자 테스트 페이지에 가깝다.

## 5. 결론

현재 구현은 방향성 측면에서 보면 다음 판단이 타당하다.

- 목표 방향성 충족도: 문서 업로드/해시/지갑 서명/Stub 앵커링 MVP까지 충족
- 최소 수정 전략: 적절함
- 구조적 정당성: 대체로 맞음
- 생산 준비도: 실제 체인 전송, 실제 분석, 운영 마이그레이션 전에는 미완성

정리하면, 지금 코드는 "문서 업로드 후 해시를 기준으로 오프체인 분석과 온체인 증명을 분기할 수 있는 MVP 기반"까지 도달했다.
다만 `Enterprise` 명칭 유지, `Role/UserType` 중복, 회사 생성 API 정책, DB migration 부재, 실제 Sepolia relayer 부재, 실제 OCR/AI 분석 부재는 아직 문서와 코드 모두에서 분명히 드러내야 할 구조적 부채다.
