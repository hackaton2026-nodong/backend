1. 현재 프로젝트에서 반드시 바꿔야 하는 방향
현재 구조는 기능별 CRUD 백엔드에 가깝다. user, document, checklist, alert, chatbot 같은 도메인이
존재하지만, 각 기능이 독립적으로 저장과 조회를 수행하는 구조로 보인다. 반면 목표 구조는 case와
document를 중심축으로 두고, 문서 처리 파이프라인과 그 결과를 checklist, dashboard, alert,
consultation으로 연결하는 오케스트레이션 백엔드다.
즉 앞으로의 리팩터링 목표는 기능 개수를 늘리는 것이 아니라, 중심축을 바꾸는 것이다. 구체적으로는
document를 단순 부가 엔티티가 아니라 가장 중요한 핵심 도메인으로 올리고, 모든 흐름이 case를 기준으로
연결되도록 만들어야 한다.

2. 유지할 것, 바꿀 것, 새로 만들 것
2.1 유지할 것
1. auth, user, cases, checklist, dashboard, alert 도메인은 완전히 버릴 필요가 없다.
2. cases 엔티티는 employer, worker, status, industry, region을 가지고 있는 시작점으로 충분히 의미가 있다.
3. dashboard에서 WORKER, EMPLOYER 분기가 이미 있다면 그 방향은 계속 살리면 된다.
4. checklist와 alert는 삭제가 아니라 document와 연결되도록 재배치해야 한다.
2.2 바꿀 것
1. document 도메인은 핵심적으로 재설계해야 한다.
2. DocumentController는 case 기반 API 구조로 바꿔야 한다.
3. DocumentService는 역할별 서비스로 나눠야 한다.
4. request.userId()를 받는 생성, 수정 패턴은 제거해야 한다.
5. chatbot은 consultation 또는 casecopilot 개념으로 재정의해야 한다.

6.2 DocumentQueryService
이 서비스는 목록, 상세, 구조화 결과, 분석 결과를 조회한다. 여기서 역할별 응답 분기를 수행할 수 있다.
@Service
@RequiredArgsConstructor
public class DocumentQueryService {
    private final DocumentRepository documentRepository;
    private final CaseAccessService caseAccessService;
    @Transactional(readOnly = true)
    public List<DocumentSummaryResponse> getCaseDocuments(Long loginUserId, Long caseId) {
        caseAccessService.validateCaseAccess(caseId, loginUserId);
        return documentRepository.findByCaseEntityId(caseId)
                .stream()
                .map(DocumentSummaryResponse::from)
                .toList();
    }
    @Transactional(readOnly = true)
    public DocumentDetailResponse getDocumentDetail(Long loginUserId, String documentId) {
        Document document = documentRepository.findById(documentId)
                .orElseThrow(() -> new IllegalArgumentException("■■■ ■■■■ ■■■■."));
        caseAccessService.validateCaseAccess(document.getCaseEntity().getId(), loginUserId);
        return DocumentDetailResponse.from(document);
    }
}
6.3 DocumentPipelineService
이 서비스가 사실상 핵심이다. 업로드 이후 파일 저장, 해시 생성, 온체인 호출, OCR 요청, 구조화 저장, AI 이벤트
발행까지 전체 흐름을 조율한다.
@Service
@RequiredArgsConstructor
public class DocumentPipelineService {
    private final FileStoragePort fileStoragePort;
    private final DocumentHashPort documentHashPort;
    private final DocumentAnchorPort documentAnchorPort;
    private final DocumentOcrPort documentOcrPort;
    private final AiHandoverPort aiHandoverPort;
    private final DocumentCommandService documentCommandService;
    private final DocumentStructuredDataService documentStructuredDataService;
    @Transactional
    public void startPipeline(String documentId, MultipartFile file) {
        StoredFile storedFile = fileStoragePort.store(file);
        documentCommandService.markStored(documentId, storedFile.storageKey(), storedFile.mimeType(), storedFile.fileSize());
        String sha256Hash = documentHashPort.generate(storedFile.storageKey());
        documentCommandService.markHashed(documentId, sha256Hash);
        AnchorResult anchorResult = documentAnchorPort.anchor(documentId, sha256Hash, Map.of());
        documentCommandService.markAnchored(documentId, anchorResult.txId());

10
        OcrExtractionResult ocrResult = documentOcrPort.extract(storedFile.storageKey(), storedFile.mimeType());
        documentStructuredDataService.saveFromOcr(documentId, ocrResult);
        documentCommandService.markOcrCompleted(documentId);
        aiHandoverPort.send(documentId);
        documentCommandService.markAnalyzed(documentId);
    }
}
중요한 점은 이 흐름 전체를 하나의 거대한 DB 트랜잭션으로 묶으면 안 된다는 것이다. 파일 저장 성공, 해시
성공, 앵커링 성공, OCR 성공은 서로 다른 실패 가능성을 가진 단계이므로, 상태 전이를 중심으로 나누어
관리해야 한다.

8.2 Controller 예시
@RestController
@RequiredArgsConstructor
@RequestMapping("/api/cases/{caseId}/documents")
public class DocumentController {
    private final DocumentCommandService documentCommandService;
    private final DocumentPipelineService documentPipelineService;
    @PostMapping(consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
    public ResponseEntity<DocumentCreateResponse> upload(
            @AuthenticationPrincipal LoginUser loginUser,
            @PathVariable Long caseId,
            @RequestPart("file") MultipartFile file,
            @RequestPart("request") CreateDocumentRequest request
    ) {
        Document document = documentCommandService.create(
                loginUser.userId(),
                caseId,
                new CreateDocumentCommand(
                        request.documentType(),
                        file.getOriginalFilename(),
                        request.issuedAt(),
                        request.expiresAt()
                )
        );
        documentPipelineService.startPipeline(document.getId(), file);
        return ResponseEntity.ok(DocumentCreateResponse.from(document));
    }
}

14. 결론
이번 리팩터링의 본질은 document를 부가 기능에서 핵심 도메인으로 승격시키는 것이다. Document가
살아나면 case, checklist, dashboard, alert, consultation까지 모두 자연스럽게 연결된다.
반대로 Document가 여전히 rawData 저장 엔티티에 머무르면, 아무리 기능을 추가해도 프로젝트의 중심축은
바뀌지 않는다. 따라서 가장 먼저 손대야 할 영역은 document 엔티티, document 서비스, document API, 권한
모델, 상태머신이다.
이 문서를 기준으로 실제 구현을 시작할 때는 먼저 엔티티와 서비스 인터페이스를 정리하고, 그 다음 업로드
API와 상태 전이를 완성한 뒤, 마지막으로 checklist와 dashboard를 연결하는 순서로 가는 것이 가장
현실적이다.
